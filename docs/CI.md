# CI locale du dépôt

Ces fichiers sont des outils de développement uniquement et ne sont pas chargés par Jeedom à l'exécution.

Les six workflows coordonnent la syntaxe PHP et PHPStan, la syntaxe frontend/ESLint/CSS, la structure Jeedom, les audits de sécurité/dépendances et la génération i18n. Certaines erreurs de syntaxe, métadonnées malformées, secrets à haute confiance et dépendances exploitables sont bloquantes. Les avertissements PHPStan, d'harmonisation de style, de migration jQuery et de conventions Jeedom sont des avertissements explicites, sans exclusions larges ni `continue-on-error`.

La CI statique ne vérifie pas les largeurs des tuiles rendues, la mise en page visuelle ou le comportement `Modification en cours…` à l'exécution ; ceux-ci nécessitent des tests navigateur.

La traduction utilise le Jeedom core épinglé et `jeedom/jeetranslate`, préserve les valeurs manuelles existantes, validate les placeholders et ouvre une PR révisable limitée à `core/i18n/*.json` et `plugin_info/info.json`. Secret de dépôt requis : `DEEPL_API_KEY`. Les PR de fork ne font que valider les traductions actuelles et ne reçoivent ni secrets ni permissions d'écriture.

`market_badges.py` régénère le bloc de badges du market Jeedom (note, prix, remise, achats, téléchargements, commentaires) dans `README.md`, entre les marqueurs `market-badges:start` et `market-badges:end`. Le workflow `Market badges` s'exécute après un push sur la branche par défaut, chaque lundi à 04:17 UTC et à la demande. Il ne commit que si une valeur a réellement changé. Le commit généré contient `[skip ci]`, pour qu'un compteur de téléchargement changeant ne relance pas la CI complète du dépôt.

Les plugins publiés épinglent `"market": {"id": <n>}` dans `ci-config.json`, évitant la découverte fragile du catalogue HTML lors des rafraîchissements normaux. Le `logicalId` du market retourné est toujours vérifié contre l'`id` du `plugin_info/info.json` du plugin à chaque exécution, pour qu'un épinglage obsolète ou incorrect ne puisse pas publier les chiffres d'un autre plugin. Les plugins non publiés conservent la découverte automatique du catalogue ; chaque candidat n'est accepté qu'après la même vérification de `logicalId` (`LG ThinQ Local` ne peut donc jamais hériter des badges de `LG ThinQ`).

Le workflow écrit uniquement pour les événements planifiés/manuels de confiance et pousse sur la branche par défaut ; les pushes sur les branches de fonctionnalités sont ignorés. Les GitHub Actions utilisent des versions majeures explicites (`actions/checkout@v7`, `actions/setup-python@v7`). Le workflow exécute `test_market_badges.py` avant de modifier le README et rebase avant de pusher. Une configuration invalide, des marqueurs malformés, une recherche ambiguë ou une panne du market affiche un avertissement et laisse `README.md` intact : un rafraîchissement de badge ne doit jamais corrompre le README ni mettre le dépôt en rouge parce que le market externe est indisponible.

`readme_badges.py` répare les badges de dépôt d'un dépôt **privé**. shields.io interroge l'GitHub API non authentifiée, donc chaque badge `img.shields.io/github/*` affiche "repo not found" sur un dépôt privé — un badge `dynamic/json` pointant vers `api.github.com` échoue identiquement. Le `GITHUB_TOKEN` fourni au workflow `README badges` *peut* lire le dépôt, donc le script résout la licence, le langage principal, le dernier commit, les issues ouvertes et les PR ouvertes une fois et réécrit ces cinq routes en badges shields.io statiques. Aucun appel à la GitHub API n'a lieu à l'affichage du README, donc les badges s'affichent pour tout le monde, dépôt privé ou non.

`github/issues` est un préfixe de `github/issues-pr`, donc les routes sont réécrites de la plus longue à la plus courte avec un garde-traîne ; sans cela, le badge des PR est silencieusement remplacé par le badge des issues. Les comptages ouverts proviennent du numéro de page `rel="last"` d'une requête `per_page=1`, donc une requête donne le total. Le workflow suit les mêmes conventions que le job des badges market : versions d'action épinglées, exécution d'un test unitaire avant l'écriture, `[skip ci]` sur le commit, rebase avant push, et `exit 0` avec un avertissement en cas de problème API.

`report_ci.py` s'exécute dans le job `report` de `ci.yml`, après tous les autres jobs et avec `always()`, uniquement sur la branche par défaut. Il lit les jobs de l'exécution courante ainsi que les annotations de check-run du commit, écrit le résumé dans `GITHUB_STEP_SUMMARY`, et crée ou met à jour une seule issue roulante intitulée `[CI] Rapport qualité automatique` au lieu de laisser une issue par échec. Quand l'exécution est propre, il commente et ferme cette issue. Les exécutions `pull_request` sont exclues car les branches de fork ne sont pas fiables et leurs annotations ne sont pas exploitables dans l'issue de la branche par défaut. Les variables d'environnement manquantes sortent en `2` ; une erreur API affiche un avertissement et sort en `0`, pour qu'un échec de rapport ne masque jamais une CI verte.

`check-php.yml`, `ci-config.json`, `phpstan.neon` et `translation.yml` portent des valeurs par plugin et sont les seuls fichiers censés différer entre les dépôts : la matrice PHP, la liste des branches, l'entrée de scan `3rdparty/Capabilities.php` et la liste de langues i18n déclarée. Tous les autres fichiers CI sont octet-identiques à travers la flotte, donc une correction faite dans un dépôt peut être copiée dans les autres sans adaptation.
